CORE ARCHITECTURE

Metric Processing and Software Alert State

The engine processes host-supplied batches and applies startup and high-energy heuristics. It does not receive machine speed or identify the physical source of a vibration change.

SAFEGUARD 01

Startup Stabilization

Baseline accumulation starts after 20 accepted evaluation windows and completes after 36 accepted windows. The engine does not monitor acceleration, speed, inrush current, or torque.

SAFEGUARD 02

High-Energy Window Heuristic

A short high-energy limiter changes metric contributions for a limited number of windows. It does not distinguish shocks from defects or guarantee a false-alert rate.

SAFEGUARD 03

Fixed Startup Baseline

The implementation collects a baseline during startup and does not update it after calibration. A new baseline requires an explicit reset by the host.

OEM FIRMWARE INTEGRATION

C API Integration

The API accepts a context and three 32-sample arrays. Host firmware is responsible for sensor acquisition, scheduling, scaling, and any response to reported states.

motor_sensor_task.c
Standard ANSI C Public API Header Integration
/* 1. Include clean public header: */
#include "ac_engine.h"

void sensor_task_process_vibration(const int32_t *x_fifo, const int32_t *y_fifo, const int32_t *z_fifo) {
    /* 2. Feed 32 accelerometer counts into engine (~4.17 us host avg / ~24k Cortex-M cycles): */
    ac_result_t result = ac_engine_feed_and_evaluate(x_fifo, y_fifo, z_fifo, 32);

    /* 3. Output to local HMI keypad screen or visual status LED: */
    lcd_set_health_display(result.health_index); /* Relative index from 0 to 100 */

    /* 4. Apply host-defined policy; the library does not control a relay: */
    if (result.condition == AC_STATE_CRITICAL_FAULT) {
        notify_operator(); /* Example host action, not a safety function */
    }
}
